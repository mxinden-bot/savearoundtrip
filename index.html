Save a round trip with HTTP/3.

HTTP/3 runs on QUIC, which sets up a secure connection in one round trip less than TCP and TLS. On a repeat visit, QUIC 0-RTT puts the request in the very first packet. Servers advertise HTTP/3, and clients race it, falling back where it does not work.

The HTTPS record is looked up in the browser, via Cloudflare's DNS-over-HTTPS. The Alt-Svc HTTP header, the live HTTP/3 handshake and 0-RTT can't be checked from a browser, so the domain is sent to a small open-source backend that runs those checks with quic-go. Nothing is stored.

One round trip less

Every new connection pays round trips for its handshakes before the request can go out. HTTP/2 runs on TCP and TLS: one handshake each. HTTP/3 runs on QUIC, a new transport protocol that does both in a single handshake, so HTTP/3 saves a round trip. On a repeat visit, QUIC 0-RTT saves another: the request goes out with the very first packet.

TLS 1.3 over TCP has 0-RTT too, but the TCP handshake still costs a round trip first.

What one round trip costs

Across Firefox users: half of all HTTP/3 connections have a round trip of 25 ms or less, and one in twenty takes longer than 118 ms.

Clients race

HTTP/3 is faster, but it does not work everywhere. Antivirus software inspects it and breaks it (bug 2034178). VPNs stall it (bug 1734110), and their DNS resolvers often do not return HTTPS records. Some networks block UDP, which is rare today (RFC 9308): QUIC works 97%+ of the time.

Which protocol works depends on the user's network, and the site cannot know. So browsers try several options at once and keep the first that connects. This is called Happy Eyeballs.

Why "Happy Eyeballs"? Eyeballs is network operator slang for users: the people looking at the screen. Eyeballs are latency sensitive, and often on lossy, bad networks.

Servers advertise

The browser can only race HTTP/3 if it knows the server supports it. Servers advertise HTTP/3 in two ways, and they differ in when the browser learns about it:

1st connection2nd3rd…
1. Alt-Svc headerin the HTTP responseHTTP/2HTTP/3HTTP/3HTTP/3
2. HTTPS DNS recordin DNS, before connectingHTTP/3HTTP/3HTTP/3HTTP/3

1 · Alt-Svc header: HTTP/3 from the second connection

The server advertises HTTP/3 in an HTTP response header (RFC 7838). The browser only learns about it from that response, so the first connection is HTTP/2. HTTP/3 starts with the second connection.

2 · HTTPS DNS record: HTTP/3 on the very first connection

The HTTPS record (RFC 9460) says the same in DNS. The browser looks it up together with the A and AAAA records, before it connects. DNS already says the server speaks HTTP/3, so the very first connection is HTTP/3 too.

The HTTPS record also carries what a header can't:

  • ECH. The record carries the keys that encrypt the TLS ClientHello, including the server name (RFC 9849). A header can't: the key is needed before the first connection.
  • IP hints. ipv4hint and ipv6hint let the browser start connecting when the HTTPS answer arrives before the A and AAAA records.
  • One source of truth, cached with a DNS TTL, instead of a per-origin header cache.

Do both: the HTTPS record for the first connection, Alt-Svc for browsers that do not look up HTTPS records.

3 · QUIC 0-RTT for the repeat visit

After an HTTP/3 connection, the server can hand the browser a session ticket that allows early data. On the next visit, the request goes out in the first packet, together with the handshake (RFC 9001).

FAQ

Does my CDN do this automatically?

Partly. Cloudflare publishes the HTTPS record automatically, CloudFront through Route 53; several CDNs need HTTP/3 turned on. The support table above has the details, and the checker shows what a domain advertises today.

Will an HTTPS record break older clients?

No. A client that doesn't understand HTTPS records ignores them and falls back to the A and AAAA records, and the Alt-Svc header.

Which browsers use the HTTPS record, and do they need DoH?

All the major engines support it, on by default, and read the record whether or not DNS-over-HTTPS is on: Safari uses the operating-system resolver, Chrome its own built-in resolver (over DoH or plain DNS), and Firefox either the operating-system resolver or its own DNS-over-HTTPS resolver.

Should I drop the Alt-Svc header?

No. Keep it as a fallback for clients that did not get the HTTPS record: older clients, and resolvers or networks that do not deliver it.
