Save a round trip with HTTP/3.

HTTP/3 runs on QUIC, which sets up a secure connection in one round trip less than TCP and TLS. On a repeat visit, QUIC 0-RTT puts the request in the very first packet. Offer HTTP/3 on the server, and the browser races it on the client, falling back where it does not work.

The HTTPS record is looked up in the browser, via Cloudflare's DNS-over-HTTPS. The Alt-Svc HTTP header, the live HTTP/3 handshake and 0-RTT can't be checked from a browser, so the domain is sent to a small open-source backend that runs those checks with quic-go. Nothing is stored. savearoundtrip.com itself publishes an HTTPS record with HTTP/3, IP hints and ECH.

one round trip less

Before the first byte of a response arrives, every new connection pays round trips for its handshakes. QUIC folds the transport and the TLS handshake into one, so HTTP/3 saves a round trip. QUIC 0-RTT saves another on a repeat visit.

Round trips until the first response byte. TLS 1.3 over TCP has 0-RTT too, but the TCP handshake still costs a round trip first.

offer on the server, race on the client

HTTP/3 is faster, but it does not work everywhere. Antivirus software inspects it and breaks it (bug 2034178), VPNs stall it (bug 1734110), and some networks block UDP (RFC 9308). QUIC works 97%+ of the time. Which protocol works depends on the user's network. The site cannot know.

So the browser races. Happy Eyeballs tries several options at once and keeps the first that connects. It started with IPv6, with IPv4 as the fallback (RFC 8305). Happy Eyeballs v3 adds HTTP/3, with HTTP/2 as the fallback. In Firefox it is on in Nightly and for 50% of Release.

Offer HTTP/3 without risk: where it breaks, the browser falls back.

The internet cannot switch all at once

"Transition is easiest when changing only one entity still benefits that entity." RFC 8170

TLS 1.3 got there that way: a client offers it, a server that supports it gains right away, and everyone else falls back to TLS 1.2. HTTP/3 works the same way.

tell the browser about HTTP/3

The browser can only race HTTP/3 if it knows the server offers it. There are two ways to say so, plus 0-RTT for the repeat visit.

Alt-Svc HTTP header

HTTP/3 from the second connection on.

HTTPS DNS record

HTTP/3 on the first connection.

Alt-Svc (RFC 7838) is an HTTP response header. The browser reads it only after a first connection over TCP, so HTTP/3 starts on the next one.

An HTTPS DNS record (RFC 9460) carries the same signal in the DNS. The browser looks it up alongside the A and AAAA records, before it connects, so even the first connection can use HTTP/3.

0-RTT for the repeat visit

After an HTTP/3 connection, the server can hand the browser a session ticket that allows early data. On the next visit, the request goes out in the first packet, together with the handshake (RFC 9001).

Recommended: publish the HTTPS record too

Keep sending Alt-Svc, and add the record. It does more than the header can:

  • HTTP/3 before the first connection, not after it.
  • ECH. The record carries the keys that encrypt the TLS ClientHello, including the server name (RFC 9849). A header can't: the key is needed before the first connection.
  • IP hints. ipv4hint and ipv6hint let the browser start connecting when the HTTPS answer arrives before the A and AAAA records.
  • One source of truth, cached with a DNS TTL, instead of a per-origin header cache.

offer HTTP/3

What the checklist above asks for, and how.

1 · Turn on HTTP/3

On the server or the CDN. QUIC runs over UDP, so open UDP port 443 in the firewall. Keep HTTP/2 on: it is the fallback.

2 · Send Alt-Svc

Alt-Svc: h3=":443"; ma=86400

HTTP/3 on port 443 of the same host; the browser may remember it for a day (ma, in seconds).

3 · Publish an HTTPS DNS record

A ServiceMode record advertising HTTP/3, with address hints:

; zone file (BIND-style)
example.com.  3600  IN  HTTPS 1 . alpn="h3,h2" ipv4hint=203.0.113.10 ipv6hint=2001:db8::10
  • example.com. the name it is published under; the trailing dot makes it fully qualified.
  • 3600 the TTL: how long resolvers may cache it, in seconds. A longer TTL keeps it cached for more visitors.
  • IN HTTPS the class and the record type (RFC 9460).
  • 1 the priority. 1 or higher is ServiceMode: this record carries the parameters. 0 is AliasMode: it points at another name, which the browser then resolves (the checker follows it too).
  • . the target host. . means the owner name itself, here example.com.
  • alpn="h3,h2" the protocols the server speaks: h3 is HTTP/3, h2 is HTTP/2.
  • ipv4hint / ipv6hint addresses the browser can start connecting to right away.

Most managed DNS providers (Cloudflare, Route 53, and others) offer the HTTPS record type directly.

4 · Turn on 0-RTT

Often a single switch: ssl_early_data on; in nginx, 0-RTT Connection Resumption on Cloudflare. Early data can be replayed, so act only on requests that are safe to repeat, and answer the rest with 425 Too Early (RFC 8470).

faq

Can turning on HTTP/3 break a site?

Not for a browser that races. Firefox with Happy Eyeballs v3 tries HTTP/3 and HTTP/2 and keeps the first that connects. Keep HTTP/2 on as the fallback.

Does my CDN do this automatically?

Some do. Cloudflare, for one, serves an HTTPS record with alpn="h3" automatically for proxied zones. Others leave it to the site. The checker shows what a domain offers today.

Will an HTTPS record break older clients?

No. A client that doesn't understand HTTPS records ignores them and falls back to the A and AAAA records, and the Alt-Svc header.

Which browsers use the HTTPS record, and do they need DoH?

All the major engines support it, on by default, and read the record whether or not DNS-over-HTTPS is on: Safari uses the operating-system resolver, Chrome its own built-in resolver (over DoH or plain DNS), and Firefox either the operating-system resolver or its own DNS-over-HTTPS resolver.

Should I drop the Alt-Svc header?

No. Keep it as a fallback for clients that did not get the HTTPS record: older clients, and resolvers or networks that do not deliver it.
