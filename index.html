You serve your site via HTTP/3.
Let clients use it on the first connection and save a round trip.

If your site serves HTTP/3, there are two ways a browser can find that out: the Alt-Svc HTTP header, which it can only read after it has already connected over HTTP/2, or an HTTPS DNS record, which it reads before connecting. Advertise only via the header and clients reach HTTP/3 only on their second connection. Publish an HTTPS record and they connect over HTTP/3 right away, on the first one. And HTTP/3 connects a round trip faster anyway: it runs over QUIC, which folds the transport and TLS handshakes into a single exchange, one round trip where TCP plus TLS needs two.

the wasted round trip

Alt-Svc (RFC 7838) is an HTTP response header. To read it, the client must finish a request, which means it has already opened a TCP connection, done a TLS handshake, and spoken HTTP/1.1 or HTTP/2. Only then does it learn "by the way, I also speak HTTP/3". The HTTP/3 upgrade lands on the next connection.

why the HTTPS record is strictly better

The HTTPS resource record (RFC 9460, Nov 2023, same wire format as SVCB) folds everything a client needs to open the optimal connection into the DNS answer it was already fetching. Concretely:

1 · HTTP/3 discovery before the first byte

The alpn SvcParam lists the ALPN protocol IDs the endpoint speaks, e.g. h3 (HTTP/3) and h2. Because it arrives during name resolution, the client can pick QUIC for its very first connection instead of discovering h3 only after an HTTP/2 round trip. An HTTPS RR can carry multiple ALPNs; an Alt-Svc field value carries one protocol each.

2 · ECH: Encrypted Client Hello (only the DNS can deliver it)

The ech SvcParam carries the endpoint's ECHConfigList public keys (draft-ietf-tls-esni). ECH encrypts the TLS ClientHello, including the SNI server name, so a network observer can't see which site you're visiting. This is a chicken-and-egg problem an HTTP header can't solve: you need the public key before you send the first ClientHello, which is exactly when no connection exists yet. Only an out-of-band channel, the DNS (the HTTPS record), can bootstrap ECH. No HTTPS RR, no ECH.

3 · IP hints: connect without a second lookup race

ipv4hint and ipv6hint ship candidate addresses inside the HTTPS answer. The client can start connecting immediately and run Happy Eyeballs v2 (RFC 8305) over them, rather than serializing an extra A/AAAA resolution step. They're especially valuable at the zone apex and for steering to the right CDN edge. Alt-Svc has no equivalent.

4 · Aliasing at the zone apex, no CNAME hacks

In AliasMode (priority 0) an HTTPS record redirects the apex of a zone, example.com itself, to another target, something a CNAME can't legally do at the apex. ServiceMode (priority ≥ 1) carries the connection parameters above. One record type does load-distribution, failover, and parameter delivery.

5 · One authoritative source, sane caching

Reachability lives in the DNS with a normal TTL, instead of being smeared across per-origin HTTP-header caches with their max-age dilemma: too long and clients use stale alternatives, too short and they fall back to older protocols more often than they should. The browser was going to do a DNS lookup anyway; this just makes that lookup carry the answer.

from real browsers

Firefox Nightly Not a model and not a scan of ours: this is Firefox itself reporting, via Mozilla's public GLAM telemetry, how it discovered HTTP/3. These numbers are Firefox Nightly only, the only channel carrying these measurements today.

A browser can learn that a server speaks HTTP/3 in two ways: from the Alt-Svc HTTP response header (seen only after it has already connected), or from an HTTPS DNS record (seen before connecting). So every connection falls into one of four groups:

  • Neither: HTTP/3 was not advertised at all.
  • Alt-Svc only: advertised, but only in the header, so the first connection could not use it.
  • HTTPS record only: advertised in DNS, so the first connection could go straight to HTTP/3.
  • Both: advertised in DNS and the header.

Can't I just check Alt-Svc too? Not from a web page. CORS forbids reading another origin's response headers in the browser. Spotting "Alt-Svc but no HTTPS RR" needs an offline scan; that's what the headline number is for.

publish one (it's two lines)

A ServiceMode HTTPS record advertising h3, with address hints:

; zone file (BIND-style)
example.com.  3600  IN  HTTPS 1 . alpn="h3,h2" ipv4hint=203.0.113.10 ipv6hint=2001:db8::10

; add ECH once you have an ECHConfigList:
;   ... alpn="h3,h2" ech="AED+DQBA..." ipv4hint=...
  • Priority 1 = ServiceMode (carries params). 0 = AliasMode.
  • . as the target means "same name as the owner".
  • Most managed DNS providers (Cloudflare, Route 53, etc.) expose an HTTPS/SVCB record type directly.
  • Verify it: paste your domain into the checker above.

faq

Does my CDN publish this automatically?

Some do. Cloudflare, for one, serves an HTTPS record with alpn="h3" automatically for proxied zones. Others leave it to you. The quickest way to find out is to check your domain above.

Will an HTTPS record break older clients?

No. A client that doesn't understand HTTPS records just ignores them and falls back to ordinary A/AAAA lookups (and your Alt-Svc header, if you still send it). Publishing one is strictly additive.

Apex or www?

Publish it on the name people actually connect to. If that's the apex (example.com), an HTTPS record works there directly. No CNAME tricks needed.

What about repeat visits?

Even better: once a client has spoken HTTP/3 with you, a return visit can resume the QUIC connection in 0-RTT, putting the first request on the wire with no handshake round trip at all.

Should I drop the Alt-Svc header?

Not yet. Keep sending it as a fallback for clients that didn't get the HTTPS record. The record just means the common case stops paying a round trip to discover what DNS could have told it up front.
